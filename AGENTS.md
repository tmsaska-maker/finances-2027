# Правила роботи над «Фінанси 2027» (рішення власниці, 18.11.2026)

Цей файл — обов'язковий контрольний список для подальшої розробки, міграцій, релізів і планування. Якщо пропонована дія суперечить правилам, спочатку зупинитися й окремо погодити зміну правила з власницею; не обходити правило технічними перейменуваннями.

## Інфраструктура: одна база, без додаткових копій

1. Використовувати **одну наявну фінансову PostgreSQL-базу** і **одну версію застосунку «Фінанси 2027» на Lightsail**. Не створювати staging/production дублікати, додаткові БД, репліки, клони, паралельні середовища, зайві контейнери або копії застосунку.
2. **Не створювати резервних копій, snapshot, дампів, архівів даних чи баз для відновлення автоматично або «про всяк випадок».** Копія для відновлення — не та сама річ, що друга робоча БД, проте обидві **не схвалені** як новий етап робіт. Нова копія можлива лише після конкретного пояснення мети й окремої прямої згоди власниці.
3. **Не ставити «створити backup» як рутинний обов'язковий пункт** в задачах/чаті/чеклісті; не подавати старі backup/snapshot артефакти як вимогу. Не видаляти вже наявні артефакти без окремого доручення.
4. Не змінювати робочу систему «Скринінг40», її PostgreSQL, gateway, Docker, Caddy, доступи та маршрути під час робіт із «Фінанси 2027».
5. Для міграції працювати з **існуючою фінансовою БД**, без другої БД: перед змінами перевірити фактичні версії `schema_migrations`, структуру таблиць, залежності й поточні дані, звірити SQL-операції з цим станом, перевірити сценарії в GitHub CI на його **тимчасовій** PostgreSQL (автоматичний одноразовий тест CI — не додаткова Lightsail база), і лише тоді вирішувати, чи можна безпечно застосувати зміни у чинній БД.
6. **Без резервної копії не заявляти гарантоване відновлення після втрати або пошкодження даних.** Додавальні й повторювані (idempotent) міграції пріоритетні, але їхня транзакційність не відновлює дані після всіх типів збоїв. Якщо зміна потенційно руйнівна або немає перевіреного способу безпечно її виконати — не запускати її самовільно; повідомити ризик, запропонувати безпечний неруйнівний варіант або попросити окреме рішення.
7. Перед будь-яким реальним запуском прямо назвати: **яка одна БД**, **які міграції**, **що вони змінюють**, **які ризики відсутності backup**, **чи був фактичний запис на сервер**, **що перевірено**. CI pass / PR merged / код у GitHub **не означає**, що реліз уже є на Lightsail.
8. Усі нові форми — в єдиному погодженому стилі Figma v0.2, зі спільними компонентами. Звітувати конкретними діями, без абстрактних формулювань.

Це правило не дозволяє приховувати ризики. Оновлювати його тільки після прямої нової домовленості з власницею.
