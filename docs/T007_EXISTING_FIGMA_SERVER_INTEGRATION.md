# T007 — існуючий Figma UI + live finance API, без дублювання

Статус: робота розпочата, **UI ще не підключено до live фінансової PostgreSQL**. Зовнішній вигляд Figma v0.2 не змінювати.

## Виявлений стан
- `src/App.tsx` зараз відображає основний `ExpensesScreen`, що працює із синтетичними demoExpenses / demo localStorage. Це **не** реальна база.
- `?financeServer=1` вмикає окремий `ServerExpenses` — суто тестовий діагностичний екран, його **не** робити фінальною копією інтерфейсу.
- `src/domain/server-expenses-api.ts` звертається до `/finance-api` через same-origin; API `server/http.mjs` очікує bearer token, який **не можна** вставляти у браузер чи публічний GitHub Pages.
- Категорії з міграцій 003–006 живуть у фінансовій PostgreSQL; `GET /categories?project=...&type=...` віддає ID, назви, ієрархію, обмеження за проєктом і типом.

## Перший технічний інкремент
`src/domain/finance-categories.ts` — протестований **read-only** типізований адаптер. Працює тільки через same-origin `/finance-api/categories`; не зберігає токен у браузері, відмовляється від некоректних чи дубльованих записів; перетворює ієрархію на підписи для наявної форми, зберігаючи стабільні ID як значення. На цьому кроці **не підключений до живого UI**, аби не змішати демодані з фактичними обліковими даними.

## Обов'язковий порядок наступних змін T007
1. Підготувати справжню користувацьку автентифікацію/авторизацію на same-origin gateway. Приватний `FINANCES_API_TOKEN` залишається лише на сервері; не робити `/finance-api` відкритим через Caddy без авторизації.
2. Під'єднати отримання категорій та зобов'язань до **того самого** `ExpensesScreen` з існуючими картками, таблицями, фільтрами, формами. Забезпечити loading/error/empty стани без зміни дизайну.
3. Прибрати демозначення як джерело фінансової істини в авторизованому режимі; не переписувати й не імпортувати localStorage автоматично.
4. Розділити стан UI та persistence; протестувати project/category ID, банківське підтвердження платежів, відмову доступу та непорушність Figma v0.2.
5. Лише після повного review — окремий деплой UI на той самий Lightsail. Реальні фінансові записи до того не вводити.

## Інкремент 2 — спільний авторизований gateway, локальний код (не DEPLOY)

- `server/browser-gateway.mjs`: окремий захищений шлюз тільки для GET `/finance-api/categories` та `/finance-api/obligations`, із входом за паролем (PBKDF2 з випадковою сіллю), HMAC-підписаною HttpOnly/Secure/SameSite=Strict cookie, 8-годинним терміном, відкликанням сесії при виході, Origin-перевіркою для входу/виходу, лімітом помилкових спроб. У браузер **не** передається FINANCES_API_TOKEN; він живе лише на сервері. Після рестарту шлюзу потрібен новий вхід.
- `server/browser-gateway-main.mjs`: окремий процес на **тому самому Lightsail**, слухає лише `127.0.0.1:8092`; Caddy/Compose/Screening40 не змінені і цей процес **ще не запускався**.
- `src/domain/finance-session.ts`: єдиний клієнт входу/виходу для **всіх** екранів майбутнього приватного UI; не зберігає пароль, токен чи cookie в localStorage. 
- Жоден публічний endpoint не підключено, жодних POST фінансових змін через gateway не дозволено. Наявні демо-Figma сторінки й дані не змінено.
- Перед приватним DEPLOY потрібні: окремий **непублічний HTTPS origin** фінансового UI; керовані серверні секрети FINANCES_PUBLIC_ORIGIN, FINANCES_SESSION_SECRET та FINANCES_OWNER_PASSWORD_HASH; Caddy reverse proxy тільки до шлюзу; перевірки TLS/cookie/session/auth, анти-CSRF і login rate-limit. Пароль не зберігати у GitHub, чаті або браузерному коді. Кешування фінансових відповідей заборонити.
- Поточний gateway лише **read-only foundation**; потрібен окремий security review до відкриття реальних записів, надійний розподілений захист від brute-force та HTTP-заголовки безпеки на HTTPS edge, якщо з'явиться зовнішній доступ.

**Важливо:** завершення цього інкремента не означає, що UI вже під'єднаний до робочих даних, ані що вхід для користувача готовий до використання. Дизайн Figma не змінювати. Наступний інкремент — безпечне з'єднання саме наявного ExpensesScreen із server read models та UX авторизації, не окремий duplicate screen.

## Інкремент 3 — read-only підключення НАЯВНОГО ExpensesScreen (підготовлено; без DEPLOY)
- `src/domain/live-finance-expenses.ts` отримує `GET /finance-api/session`, перевіряє приватну сесію, тоді читає `GET /finance-api/obligations` лише через той самий origin, не записуючи token, cookie чи фінансові дані в localStorage.
- Валідація read-model fail-closed: жодних демоданих як fallback; заборонено змішувати UAH з USD/EUR у гривневих KPI, неточні великі суми та неповні вибірки (500+ записів). Поле serverId зберігається у view-model для майбутньої серверної роботи, локальний числовий id використовується **лише** для тимчасової навігації картки.
- `src/App.tsx` використовує **той самий Figma ExpensesScreen** у приватному Vite-білді, якщо `VITE_FINANCES_PRIVATE_UI=true`: завантажує read-only server model, виводить loading/error/empty, ховає дії створення/платежів, **не читає і не змінює** демо-localStorage; чинний дизайн і компоненти Figma збережено. `?financeServer=1` у приватному білді недоступний.
- За замовчуванням звичайний збірковий режим — **демо**, включно з GitHub Pages. `VITE_FINANCES_PRIVATE_UI` — **прапорець збірки, а не автентифікація**: захист забезпечує gateway.
- Перед приватним DEPLOY — ще потрібні HTTPS gateway, тестування на тому самому origin, UI входу/виходу для всіх екранів, підтримка валют/пагінації, покриття інших екранів, дії запису з CSRF/авторизацією та погоджений UX. Цей інкремент **лише читання**, жодних реальних записів не внесено.

Лише тоді — окреме ручне схвалення деплою та відкат.

## 16.11 — фактичний HTTPS edge (ручний inspect-edge №43821637005)

## 16.11.2026 — визначення причини HTTP 403 (після manual №43898524607)

Підтверджено: finance API localhost:8091 анонімно повертає HTTP 401, а localhost:8092 повертає HTTP 403 для `GET /finance-api/session`, `/obligations`, `/categories`. Caddy має маршрут до 8092, але не до 8091. В поточному `server/browser-gateway.mjs` анонімний GET session без Origin має повертати HTTP 200 з `authenticated:false`, отже **фактичний процес / конфігурація 8092 відрізняються від поточного коду** або спрацьовує інший захисний шар. Це розбіжність, не підтвердження успішного user login. Публічний приватний UI не деплоїти.

Діагностика `inspect-edge` доповнена тільки **читанням**: клас команди процесу 8092 (поточний запропонований gateway чи інший Node/gateway), приналежність його working directory до відомого finance/screening/other каталогу; три анонімні `GET /finance-api/session` з локальним Host, очікуваним Host та HTTPS-proxy-подібними заголовками. Виводяться лише HTTP код та клас відповіді, ніколи **не** PID, аргументи команд, паролі, вміст відповіді чи Caddyfile. Зміни сервісів/Firewall/Caddy/Screеning40 заборонені. Далі після фактичних результатів — окремо затвердити інженерне рішення, перш ніж змінювати доступ.
